01 · Foundations

Algorithmic complexity attacks

An algorithmic-complexity attack supplies inputs that make a program consume unusually large amounts of CPU time or memory. A small input can sometimes trigger a disproportionate amount of work.

CPU

Excessive computation

An input triggers slow searches, repeated backtracking, or expensive operations.

Memory

Excessive allocation

An input causes a program to allocate or retain large amounts of memory.

Availability

Service disruption

Resource exhaustion can cause delays, errors, or outages.

04 · Information leakage

Side-channel attacks

A side-channel attack infers information from observable effects of a system's operation rather than relying solely on its intended output. These effects can reveal secrets when implementation behavior depends on sensitive data.

Timing

Differences in operation duration may reveal which computations or comparisons occurred.

Cache behavior

Memory access patterns can affect cache state and execution time.

Power use

Changes in electrical power consumption can correlate with internal operations.

Electromagnetic emissions

Electromagnetic signals from hardware can leak information about computations.

Acoustic signals

Sounds from devices can sometimes correlate with their operations.

Data remanence

Sensitive data may remain recoverable in memory or storage after use if not handled properly.

Optical observation

Light emissions or visible indicators can reveal aspects of device activity.

Differential fault analysis

Comparing normal and faulty computations can reveal information about internal state.

Active and passive methods

Passive methods observe behavior; active methods deliberately influence a system, such as by inducing faults.

Why side channels matter

A cryptographic algorithm may be mathematically sound while a particular implementation leaks information through timing, cache access, power consumption, or another physical or operational signal.

Constant-time comparison idea

A constant-time comparison aims to avoid leaking information through early exits based on secret-dependent mismatches.

Constant-time goal:

Real constant-time behavior depends on compiler output, hardware, memory access, and the full implementation. Prefer well-reviewed cryptographic libraries.

06 · Mitigation

Countermeasures and trade-offs

Use robust algorithms

Choose data structures and algorithms with suitable worst-case behavior. Avoid relying only on average-case performance when inputs may be adversarial.

Apply resource limits

Set bounds on input size, nesting depth, execution time, memory use, and decompressed output. Rate-limit expensive operations.

Choose safer regex engines

For untrusted input, consider engines with predictable execution guarantees, such as RE2 where its supported syntax fits the use case.

Use constant-time routines

Use established cryptographic libraries and comparison functions designed to reduce secret-dependent timing leakage.

Reduce information exposure

Use uniform authentication responses, limit detailed error messages, and avoid exposing unnecessary timing or system-state information.

Test and monitor

Profile worst-case inputs, test resource ceilings, keep dependencies updated, and monitor abnormal CPU and memory usage.

Operations that can complicate constant-time behavior

Branches, secret-dependent memory access, division, shifts, multiplication, compiler optimizations, and hardware-specific behavior can affect timing. No single coding rule guarantees constant-time execution on every platform.

Randomization

Randomization can make some attacks harder, such as by reducing predictability of hash placement. It is not a universal fix: it should complement sound algorithms, limits, and careful implementation.

Practical principle:

Design for adversarial inputs, make expensive work bounded, avoid secret-dependent behavior where it matters, and verify the implementation rather than relying on assumptions.
